# HLB-004.1 — Reliability Contract

**Status:** Canonical contract candidate
**Baseline:** `8958a28` (`HLB-001`–`HLB-003.5` complete)
**Scope:** Hermes Life Bridge only
**Schema version:** `v0.4`

## 1. Purpose

HLB-004.1 defines the durable reliability vocabulary that later HLB-004 implementation must obey. It does **not** implement a retry engine, durable outbox, provider reconciliation, route-freshness algorithm, or Hermes capability probes.

The bridge remains a vendor-specific adapter:

> Life Runtime owns why / whether. Hermes Life Bridge owns how.

No Concern, Memory, Identity, Personality, Motivation, Contact governance, or other Life Runtime authority is introduced here.

## 2. Core distinction: `FAILED_SAFE` vs `DELIVERY_UNKNOWN`

This distinction is normative.

### `FAILED_SAFE`

`FAILED_SAFE` means HLB has positive evidence that the failed attempt did not produce an externally visible contact delivery.

Examples include a local validation failure before invocation, failure to spawn/connect before provider invocation, or an explicit provider rejection whose contract guarantees that no message was accepted.

`FAILED_SAFE` **may** become retryable, but only when the Contact `RetryPolicy` allows it and the bounded attempt budget remains.

### `DELIVERY_UNKNOWN`

`DELIVERY_UNKNOWN` means provider invocation may have occurred, but HLB cannot prove whether external delivery happened.

Examples include:

- provider send timeout after invocation may have started;
- bridge crash after provider send but before receipt persistence;
- connection loss after dispatch with no authoritative provider result;
- an ambiguous Hermes/provider response that cannot prove non-delivery.

`DELIVERY_UNKNOWN` is **not a retryable failure state**. It requires explicit reconciliation. HLB must never convert it to `FAILED_SAFE` merely because time passed or the process restarted.

For `RetryClass.CONTACT`, a `RetryPolicy` with `retry_after_delivery_unknown=true` is invalid by contract.

## 3. Contract types

### `RetryClass`

| Value | Meaning |
| --- | --- |
| `percept` | Hermes Gateway → Life Runtime percept ingestion |
| `cognition` | Life Runtime → Hermes cognition request/receipt path |
| `contact` | Governed Life Runtime contact decision → Hermes provider send |

Each class receives an independent bounded policy. A single generic blind retry loop is forbidden.

### `OperationState`

| State | Meaning |
| --- | --- |
| `prepared` | Durable operation exists and has not started an attempt |
| `in_flight` | An attempt is executing and its final outcome is not known yet |
| `retry_wait` | A `FAILED_SAFE` contact attempt has a bounded retry scheduled for `next_attempt_at` |
| `completed` | Terminal successful operation |
| `failed_safe` | Current attempt is known not to have produced an unsafe external side effect |
| `delivery_unknown` | Contact-only ambiguous provider outcome; reconciliation required |
| `exhausted` | Bounded retry budget ended after safe failures |

Normative contact transition skeleton:

```text
prepared
  ↓
in_flight
  ├─ provider confirmed accepted ──────────────→ completed / delivered
  ├─ proven no external delivery ─────────────→ failed_safe
  │                                               ├─ policy+budget → retry_wait → prepared
  │                                               └─ no budget     → exhausted
  └─ may have delivered, cannot prove outcome ─→ delivery_unknown
                                                  ↓
                                             reconciliation
```

There is no direct automatic transition from `delivery_unknown` to `retry_wait`. Reconciliation may move `delivery_unknown` only to `completed` (delivery proven) or `failed_safe` (non-delivery proven).

### `DeliveryOutcome`

| Value | Meaning |
| --- | --- |
| `not_attempted` | No final provider delivery outcome exists yet |
| `delivered` | Provider acceptance/delivery was authoritatively confirmed |
| `failed_safe` | Provider delivery is known not to have occurred |
| `delivery_unknown` | Provider delivery may or may not have occurred |

`DeliveryOutcome` is Contact-only metadata. Percept and Cognition operations must not populate it.

### `RetryPolicy`

Fields:

```text
retry_class
max_attempts
initial_backoff_seconds
max_backoff_seconds
backoff_multiplier
jitter_ratio
retry_after_failed_safe
retry_after_delivery_unknown
requires_durable_state
reconcile_before_retry
```

Contract rules:

1. `max_attempts >= 1`; unlimited attempts cannot be represented.
2. Backoff is bounded by `max_backoff_seconds`.
3. `0 <= jitter_ratio <= 1`.
4. Contact cannot set `retry_after_delivery_unknown=true`.
5. HLB-004.3 must define separate Percept/Cognition/Contact policy instances.
6. Later retry execution must remain observable and persist state when `requires_durable_state=true`.
7. If `reconcile_before_retry=true`, the engine must first check for an already accepted/persisted authoritative result before issuing another attempt.

The exact default attempt counts and backoff durations are intentionally left to HLB-004.3, where they can be validated with failure injection instead of being guessed in the contract phase.

### `BridgeOperation`

Privacy-minimized durable operation identity:

```text
operation_id
kind                    # RetryClass
idempotency_key
request_hash
state
attempt
created_at
updated_at
next_attempt_at
last_error_code
delivery_outcome        # Contact only
schema_version
```

`attempt=0` means no attempt has started. `max_attempts` belongs to the selected `RetryPolicy`, not to the operation record.

The operation record must **not** store raw user messages, cognition prompt or output text, exact contact route, `SessionSource`, Hermes `Platform.*` objects, or arbitrary Python object representations. `last_error_code` is a bounded token only; provider stderr, exception text, route details, or free-form error messages are forbidden in that field.

Every serialized contract object passes the HLB-003.5 canonical operational representation boundary.

### `RouteStatus`

| Value | Meaning |
| --- | --- |
| `unknown` | No usable route evidence exists |
| `fresh` | Route evidence is current under the route policy |
| `stale` | Route was once valid but exceeds freshness policy or lacks recent confirmation |
| `invalid` | Explicit evidence says the route must not be used |

Only `fresh` is eligible for automatic contact delivery. `unknown`, `stale`, and `invalid` must not be silently guessed or converted into a target.

The freshness algorithm itself is not part of HLB-004.1.

### `HermesCompatibilityReport`

Fields:

```text
hermes_version
plugin_api_version
gateway_hook_supported
session_source_supported
api_server_supported
send_supported
platforms[]
warnings[]
blocking_issues[]
supported
observed_at
schema_version
```

A report marked `supported=true` cannot contain `blocking_issues`. A report marked `supported=false` must contain at least one explicit blocking issue.

A later compatibility probe may discover partial capability health (for example Ingress healthy, Cognition degraded, Contact healthy). HLB-004.1 only defines the discovery result contract; capability discovery and Doctor vNext are HLB-004.5 and HLB-004.6.

## 4. Retry semantics by action class

### Percept

Percept retry is allowed only through the existing deterministic correlation / idempotency boundary. Reconnect must not create a second canonical percept.

### Cognition

Cognition may retry only if no accepted authoritative receipt already exists for the task/idempotency key. Later implementation should reconcile the receipt store before retry when the previous attempt outcome is uncertain.

A duplicate computation is undesirable but is not equivalent to duplicate external user contact; nevertheless it remains bounded and observable.

### Contact

Contact has the strictest semantics:

```text
known not sent      → FAILED_SAFE       → bounded policy may retry
confirmed sent      → DELIVERED         → completed; never resend
may have been sent  → DELIVERY_UNKNOWN  → reconcile; never blind retry
```

Process restart does not reset this distinction.

## 5. Crash-boundary rules

| Failure point | Required classification |
| --- | --- |
| Crash before provider invocation | `FAILED_SAFE` or resumable `prepared`, depending on durable reservation point |
| Provider invocation rejected with authoritative no-send result | `FAILED_SAFE` |
| Provider call times out after invocation may have started | `DELIVERY_UNKNOWN` |
| Provider succeeds and receipt is durably persisted | `completed` / `delivered` |
| Provider succeeds, then process crashes before receipt persistence | `DELIVERY_UNKNOWN` after recovery unless provider reconciliation proves delivery |
| Restart finds `in_flight` Contact operation with no authoritative receipt | `DELIVERY_UNKNOWN`, never automatic resend |

For Percept/Cognition, HLB-004.3 may define different recovery paths because those classes have different side-effect/idempotency properties.

## 6. Hard invariants carried forward

1. No duplicate external contact.
2. Unknown provider outcome is never blindly retried.
3. Retry is bounded.
4. Required retry state survives restart.
5. Ingress remains idempotent across reconnect.
6. Route is never guessed.
7. Stale/invalid routes cannot silently deliver.
8. Runtime-specific Python repr never enters operational storage.
9. Exact route remains private.
10. Bridge crash cannot mutate canonical Life Runtime authority.
11. HLB remains a Hermes-specific adapter.
12. HLB does not acquire Concern/Memory/Identity/Personality/Motivation authority.
13. Compatibility failure is explicit.

## 7. Next implementation milestone

HLB-004.2 may implement the durable operation store against these types. It must persist only canonical, privacy-minimized `BridgeOperation` data and must preserve `delivery_unknown` across process restart.
