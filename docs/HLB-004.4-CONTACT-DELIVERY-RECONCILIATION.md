# HLB-004.4 — Contact Delivery Reconciliation

**Status:** Implemented
**Canonical parent:** `8eb43c5` — HLB-004.3 Retry Engine
**Scope:** Hermes Life Bridge Contact reliability only

## Purpose

HLB-004.4 closes the most dangerous Contact failure boundary:

```text
provider invocation may have happened
↓
HLB loses the authoritative response
↓
DELIVERY_UNKNOWN
```

The bridge must never convert this state into a retry merely because a timeout, restart, or duplicate request occurred.

## Outcome classification

Hermes send failures are divided into two classes.

### `HermesSendFailedSafe`

HLB has positive evidence that the Hermes child/provider invocation never started, for example an OS-level spawn/exec failure.

```text
IN_FLIGHT → FAILED_SAFE → bounded Contact retry policy
```

### `HermesSendOutcomeUnknown`

Hermes may have executed and the provider may have accepted the message. Examples:

- subprocess timeout after invocation;
- Hermes returns non-zero after it already executed;
- unexpected sender exception after the durable attempt boundary.

```text
IN_FLIGHT → DELIVERY_UNKNOWN
```

A non-zero Hermes exit is deliberately **not** interpreted from stderr text as safe non-delivery.

## Reconciliation evidence

`ContactEvidence` has only three outcomes:

```text
DELIVERED
NOT_DELIVERED
UNKNOWN
```

Only authoritative evidence may move `DELIVERY_UNKNOWN`.

```text
DELIVERY_UNKNOWN
├─ DELIVERED     → COMPLETED
├─ NOT_DELIVERED → FAILED_SAFE → HLB-004.3 retry policy
└─ UNKNOWN       → remain DELIVERY_UNKNOWN
```

There is no time-based or restart-based fallback from UNKNOWN to FAILED_SAFE.

## Evidence sources

HLB checks evidence in this order:

1. durable local `DeliveryReceipt` already committed in `ContactStore`;
2. previously persisted decisive reconciliation evidence;
3. optional provider/Hermes evidence probe supplied by a supported adapter;
4. otherwise `UNKNOWN`.

The current generic Hermes CLI does not expose an authoritative historical message-query contract that HLB can safely assume. Therefore the default probe is intentionally absent. Unsupported providers remain locked in `DELIVERY_UNKNOWN` rather than being guessed.

## Crash ordering

Successful Contact uses this durable ordering:

```text
OperationStore: PREPARED
↓
OperationStore: IN_FLIGHT (attempt += 1)
↓
Hermes/provider send
↓
ContactStore: DeliveryReceipt committed
↓
OperationStore: COMPLETED
```

This creates two safe crash cases.

### Crash before receipt commit

Provider may have delivered, but HLB has no durable proof:

```text
restart → DELIVERY_UNKNOWN
```

No blind resend.

### Crash after receipt commit, before COMPLETED commit

Startup recovery first conservatively converts interrupted Contact `IN_FLIGHT` to `DELIVERY_UNKNOWN`, then local receipt reconciliation proves delivery:

```text
DELIVERY_UNKNOWN + durable DeliveryReceipt → COMPLETED
```

No second provider call.

## Duplicate request behavior

If the same governed Contact request is submitted again:

- durable delivered receipt → return duplicate receipt, no send;
- `DELIVERY_UNKNOWN` → reconcile, no send while unresolved;
- `RETRY_WAIT` before due time → return `contact_retry_deferred`;
- `FAILED_SAFE` → schedule bounded retry;
- `EXHAUSTED` → return `contact_delivery_exhausted`;
- `IN_FLIGHT` → return `contact_operation_in_flight`.

## Retry payload privacy

HLB does not persist raw Contact message text in the operation DB or reconciliation record.

A safe retry therefore requires the upstream governed request to be resubmitted with the same idempotency identity and request hash. The retry engine persists **eligibility**, not private message payload.

This keeps:

```text
message text
exact route
prompt/output content
```

out of the reliability ledger.

## Reconciliation persistence

`ContactStore` now includes a minimal reconciliation table:

```text
idempotency_key
outcome
evidence source
provider_message_id
observed_at
```

It stores no message body or exact target.

Conflicting decisive evidence for the same idempotency key is rejected instead of overwritten.

## Trace compatibility

New diagnostic stages:

```text
CONTACT_FAILED_SAFE
CONTACT_DELIVERY_UNKNOWN
CONTACT_RECONCILIATION_FAILED
```

The existing generic `CONTACT_FAILED` event is retained for backward-compatible diagnostics. All Contact traces continue to store only target platform/redacted markers and error fingerprints, never raw route or message text.

## Startup recovery

The Contact service owner calls `recover_startup()` before opening its Unix socket.

It:

1. finds interrupted Contact `IN_FLIGHT` operations;
2. conservatively marks them `DELIVERY_UNKNOWN`;
3. attempts authoritative reconciliation;
4. resolves delivered evidence to `COMPLETED`;
5. resolves proven non-delivery to `FAILED_SAFE` and the bounded retry policy;
6. leaves unresolved outcomes locked.

Already-existing `DELIVERY_UNKNOWN` rows remain locked and are re-evaluated only when explicit reconciliation/process traffic provides evidence.

## Hard invariants

1. Timeout after send invocation never implies safe retry.
2. Hermes non-zero exit never implies safe retry solely from stderr wording.
3. OS spawn failure is retryable as `FAILED_SAFE`.
4. `DELIVERY_UNKNOWN` cannot automatically resend.
5. Durable receipt can heal crash-after-receipt-before-completion.
6. Reconciliation UNKNOWN leaves state unchanged.
7. Only authoritative NOT_DELIVERED evidence can unlock bounded retry.
8. Duplicate governed request never bypasses existing operation state.
9. Decisive reconciliation evidence is durable and conflict-safe.
10. Reliability persistence contains no raw message body or exact target.
11. Contact retry remains capped by HLB-004.3.
12. Contact service startup recovery never treats absence of evidence as non-delivery.
