# HLB-004.5 — Hermes Compatibility Discovery

**Status:** Implemented
**Canonical parent:** HLB-004.4 Contact Delivery Reconciliation

## Purpose

HLB no longer assumes that a Hermes upgrade preserves every integration capability. It discovers and publishes what the installed Hermes actually supports.

The discovery model prefers observed capability evidence over hard-coded version allowlists.

## Evidence

The HLB plugin records privacy-minimized evidence when:

- the plugin API successfully registers `pre_gateway_dispatch`;
- the CLI fallback hook registers;
- the gateway hook is actually observed;
- a structured SessionSource with platform + chat id is successfully observed.

Only booleans, timestamps, and platform names are persisted. Exact chat ids, message ids, messages, and routes are never written to compatibility evidence.

## Runtime probes

Discovery checks:

- `hermes --version`;
- `hermes send --help`;
- Hermes API health;
- HLB plugin-registration evidence;
- gateway-hook observation evidence;
- SessionSource evidence from the compatibility evidence file or the private RouteStore;
- observed/configured platforms.

The RouteStore may prove that SessionSource routing has worked, but the exact private route is never copied into the compatibility report.

## Blocking vs warning

Core blockers include:

```text
hermes_cli_unavailable
gateway_hook_registration_unobserved
contact_delivery_enabled_but_send_unavailable
```

Examples of degradations/warnings:

```text
hermes_version_unparseable
hermes_api_unavailable
hermes_send_unavailable
gateway_hook_not_yet_observed
session_source_not_yet_observed
```

This distinction lets Doctor vNext report Ingress, Cognition, and Contact independently rather than turning every partial outage into a single binary failure.

## Version behavior

A version string is reported when parseable, but HLB does not automatically reject a new Hermes version solely because it is new. Capability probes are authoritative.

If a version cannot be parsed, HLB reports `unknown` and a warning instead of guessing.

## Published report

The latest `HermesCompatibilityReport` is written to:

```text
$XDG_STATE_HOME/hermes-life-bridge/compatibility.json
```

Plugin capability evidence is written separately to:

```text
$XDG_STATE_HOME/hermes-life-bridge/compatibility-evidence.json
```

Both are mode `0600`.

## CLI

```text
hermes-life compatibility
```

runs discovery and returns non-zero when core compatibility is blocked.

## Hard invariants

1. Hermes version alone is not treated as compatibility proof.
2. Plugin registration is observed rather than assumed.
3. Gateway hook invocation is observable separately from registration.
4. SessionSource support is evidence-based.
5. Exact route never enters the compatibility report/evidence file.
6. Contact delivery cannot be reported supported when delivery is enabled but `hermes send` is unavailable.
7. API outage may degrade Cognition without falsely declaring the core plugin incompatible.
8. Compatibility report and evidence are private mode `0600`.
9. Plugin evidence failures never break Hermes normal message flow.
