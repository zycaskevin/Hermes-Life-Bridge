# HLB-004.2 — Durable Operation Store

**Status:** Implemented
**Canonical parent:** `eefc0a8` — HLB-004.1 Reliability Contract
**Scope:** Hermes Life Bridge operational reliability only
**Store schema version:** `1`
**Bridge contract schema:** `v0.4`

## 1. Purpose

HLB-004.2 turns the HLB-004.1 `BridgeOperation` state model into crash-safe operational persistence.

It answers:

> If an HLB process disappears after an operation was reserved, started, failed safely, or became ambiguous, can the next process recover the exact reliability state without guessing or repeating an unsafe external action?

The answer must be yes.

This store is **not** canonical Life Runtime state, memory, workflow, or contact governance. It persists only the minimum operational facts needed for HLB reliability.

## 2. Storage location

New configuration:

```text
HLB_OPERATION_DB
```

Default:

```text
$XDG_STATE_HOME/hermes-life-bridge/operations.sqlite3
```

The installer publishes this path into `hermes-life-bridge.env`, but HLB-004.2 does not yet connect the store to ingress, cognition, or contact service execution paths. That wiring belongs to later HLB-004 milestones.

## 3. SQLite durability profile

`OperationStore` uses:

```text
journal_mode = WAL
synchronous = FULL
secure_delete = ON
foreign_keys = ON
busy_timeout = 5000 ms
```

The DB and SQLite sidecars (`-wal`, `-shm`) are forced to mode:

```text
0600
```

State mutation uses `BEGIN IMMEDIATE` transactions so concurrent bridge processes cannot both advance the same durable operation from the same prior state.

## 4. Durable schema

Table:

```text
bridge_operations
```

Fields:

```text
operation_id
kind
idempotency_key
request_hash
state
attempt
next_attempt_at
delivery_outcome
last_error_code
created_at
updated_at
schema_version
```

There are deliberately no columns for:

```text
message
prompt
output
payload
target
chat_id
thread_id
provider stderr
runtime object repr
```

This is an operational state ledger, not an outbox containing private content.

## 5. Idempotent reservation

`reserve()` accepts only an initial:

```text
state   = prepared
attempt = 0
```

For a repeated `(kind, idempotency_key)`:

```text
same request_hash
    → return the existing durable operation
    → created = false

different request_hash
    → OperationConflictError
```

The first durable `operation_id` remains authoritative. A duplicate caller does not create a second operation merely because it generated a different local operation ID.

Reusing an already-owned `operation_id` for a different logical operation is also rejected.

## 6. Durable identity privacy boundary

Before an initial operation touches SQLite:

1. `operation_id` and `idempotency_key` must survive HLB-003.5 canonicalization unchanged.
2. Runtime representations such as `SessionSource(...)` / `Platform.*` are rejected rather than silently rewritten into a different durable identity.
3. Values that directly look like exact messaging routes, for example:

```text
feishu:<chat_id>
telegram:<chat_id>
```

are rejected as operation identifiers.

The store never needs the exact route to perform reliability bookkeeping.

## 7. Attempt boundary

`start_attempt()` is the durable boundary before actual execution.

Transition:

```text
prepared
    ↓ atomic commit
in_flight
attempt += 1
```

Later service integration must persist `in_flight` **before** invoking the provider or external execution path.

This intentionally prefers a conservative false-positive ambiguity over an unsafe duplicate:

```text
commit in_flight
↓
process crashes before provider invocation
↓
restart sees unresolved Contact in_flight
↓
delivery_unknown
```

That message may in fact never have been sent, but the bridge cannot prove it from its own durable boundary and therefore must not guess.

## 8. State mutation API

HLB-004.2 persists only transitions allowed by the HLB-004.1 state graph.

Implemented store transitions:

```text
start_attempt
prepared → in_flight

mark_completed
in_flight → completed
or delivery_unknown → completed after reconciliation evidence

mark_failed_safe
in_flight → failed_safe
or delivery_unknown → failed_safe after reconciliation evidence

mark_delivery_unknown
contact in_flight → delivery_unknown

schedule_retry
failed_safe → retry_wait

make_retry_ready
retry_wait → prepared

mark_exhausted
failed_safe → exhausted
```

`schedule_retry()` does **not** select a retry policy, calculate backoff, or execute a retry. It only persists a schedule already chosen by a later retry engine.

`make_retry_ready()` does not increment `attempt`; only `start_attempt()` does.

## 9. `FAILED_SAFE` remains the retry gate

The store makes the HLB-004.1 rule durable:

```text
FAILED_SAFE
    ↓
schedule_retry()
    ↓
RETRY_WAIT
```

But:

```text
DELIVERY_UNKNOWN
    ✕
RETRY_WAIT
```

`schedule_retry()` requires the current durable state to be `failed_safe`.

Therefore process restart cannot erase ambiguity and turn it into an automatic resend opportunity.

## 10. Contact crash recovery

HLB-004.2 exposes:

```text
recover_interrupted_contact_operations(recovered_at=...)
```

It converts only:

```text
kind  = contact
state = in_flight
```

to:

```text
state            = delivery_unknown
delivery_outcome = delivery_unknown
last_error_code  = process_restart_in_flight
```

It deliberately does **not** modify Percept or Cognition `in_flight` operations. Their retry/reconciliation semantics belong to HLB-004.3.

The recovery method is not automatically invoked merely by opening the DB. The Contact owner must call it during its own startup/recovery sequence. This prevents one HLB process from reclassifying another service's still-live operation simply because they share the same SQLite store.

HLB-004.4 will integrate authoritative receipt/provider reconciliation around this primitive.

## 11. Reconciliation transitions

`delivery_unknown` remains durable across close/reopen.

Only evidence may resolve it:

```text
delivery_unknown
    ├─ delivery proven     → completed / delivered
    └─ non-delivery proven → failed_safe
```

No time-based expiry changes it to `failed_safe`.
No restart changes it to `prepared`.
No retry scheduler may consume it directly.

## 12. Retry state survives restart

A persisted retry retains:

```text
state = retry_wait
attempt
next_attempt_at
last_error_code
delivery_outcome = failed_safe   # Contact
```

After reopen, the same state is reconstructed as typed `BridgeOperation` values.

The retry engine in HLB-004.3 may later select due operations, but HLB-004.2 itself performs no timing/backoff policy.

## 13. Concurrency semantics

Two `OperationStore` instances may point to the same DB.

For state mutation:

```text
BEGIN IMMEDIATE
↓
load current row
↓
validate allowed transition
↓
compare current state + attempt
↓
UPDATE exactly one row
↓
COMMIT
```

A competing second start cannot increment the same attempt twice.

Expected outcome:

```text
one caller → started
one caller → OperationStateConflict
attempt    → 1
```

## 14. Schema compatibility

SQLite `PRAGMA user_version` is used for the durable store schema.

Current:

```text
user_version = 1
```

If an older HLB binary encounters:

```text
user_version > supported version
```

it fails closed with:

```text
operation_store_schema_newer_than_supported
```

It must not silently downgrade the schema marker.

## 15. Hard invariants implemented here

1. Durable operation reservation survives restart.
2. Same idempotency key cannot represent a different request hash.
3. One operation attempt cannot be started twice concurrently.
4. Attempt count increments only at the durable start boundary.
5. `delivery_unknown` survives restart.
6. `delivery_unknown` cannot be scheduled for retry.
7. Restarted unresolved Contact `in_flight` can be conservatively classified `delivery_unknown`.
8. Contact recovery does not mutate Percept/Cognition operations.
9. Retry-wait schedule and attempt count survive restart.
10. Terminal `completed` / `exhausted` operations cannot restart execution.
11. Runtime Python representations do not enter the store.
12. Exact route-shaped identities are rejected.
13. No message/prompt/route payload columns exist.
14. DB/WAL/SHM are private mode `0600`.
15. Future schema versions fail closed.

## 16. Explicit non-goals

HLB-004.2 does not implement:

```text
retry policy selection
backoff calculation
jitter
retry scheduler loop
provider retry
provider reconciliation
Hermes compatibility discovery
Doctor vNext
route freshness
service startup integration
failure-injection framework
soak testing
```

It also does not implement any Life Runtime Concern, Memory, Identity, Personality, Motivation, or ContactDecision authority.
