# HLB-004.3 — Retry Engine

**Status:** Implemented
**Canonical parent:** `c8db2f4` — HLB-004.2 Durable Operation Store
**Scope:** Hermes Life Bridge retry policy, scheduling, and non-Contact restart recovery
**Does not execute providers:** yes

## 1. Purpose

HLB-004.3 adds a bounded retry policy/scheduler over the durable `OperationStore`.

It answers four questions:

1. Is this operation class allowed to retry?
2. How many total attempts may it make?
3. How long must it wait before another attempt becomes eligible?
4. What reconciliation must happen before another attempt may start?

The Retry Engine never calls Hermes, Life Runtime, or an external messaging provider. It changes durable reliability state only.

```text
FAILED_SAFE
    ↓ RetryEngine
RETRY_WAIT
    ↓ due
PREPARED
    ↓ begin_attempt durable boundary
IN_FLIGHT
    ↓ executor belongs elsewhere
actual operation
```

This separation prevents the scheduler itself from becoming an external side-effect executor.

## 2. Explicit action-class policies

HLB does not have one generic retry policy.

### Percept

```text
max_attempts              = 5
initial_backoff_seconds   = 0.25
max_backoff_seconds       = 4.0
backoff_multiplier        = 2.0
jitter_ratio              = 0.20
retry_after_failed_safe   = true
requires_durable_state    = true
reconcile_before_retry    = false
```

Reasoning:

- Percept ingestion already has deterministic idempotency/correlation.
- A repeated transport attempt must not create a second canonical Runtime percept.
- Short retry delays are appropriate because local Runtime socket restarts are expected to be brief.

### Cognition

```text
max_attempts              = 3
initial_backoff_seconds   = 1.0
max_backoff_seconds       = 8.0
backoff_multiplier        = 2.0
jitter_ratio              = 0.20
retry_after_failed_safe   = true
requires_durable_state    = true
reconcile_before_retry    = true
```

Reasoning:

- Cognition can be expensive.
- Duplicate computation is less dangerous than duplicate external contact, but should remain bounded.
- HLB must check for an accepted `CognitiveReceipt` before scheduling or starting a retry.

### Contact

```text
max_attempts              = 2
initial_backoff_seconds   = 2.0
max_backoff_seconds       = 8.0
backoff_multiplier        = 2.0
jitter_ratio              = 0.20
retry_after_failed_safe   = true
retry_after_delivery_unknown = false
requires_durable_state    = true
reconcile_before_retry    = false
```

Contact gets at most one retry after the first attempt, and only from a positively classified `FAILED_SAFE` state.

`reconcile_before_retry=false` here is deliberate: a Contact operation cannot reach the retry scheduler from `DELIVERY_UNKNOWN`. HLB-004.4 owns that reconciliation. Once HLB-004.4 proves non-delivery, it may resolve the operation to `FAILED_SAFE`; only then does the normal Contact retry policy apply.

## 3. Bounded attempts

`max_attempts` counts total attempts, not retries.

Example Contact:

```text
attempt 1
    ↓ FAILED_SAFE
retry allowed
    ↓
attempt 2
    ↓ FAILED_SAFE
EXHAUSTED
```

There is no attempt 3.

Example Cognition:

```text
attempt 1
attempt 2
attempt 3
EXHAUSTED
```

Percept is bounded at five total attempts.

## 4. Backoff

After failed attempt `N`, the nominal delay is:

```text
initial_backoff × multiplier^(N-1)
```

capped at:

```text
max_backoff_seconds
```

The final jittered delay is also capped at the same maximum.

HLB does not use unbounded exponential growth.

## 5. Deterministic jitter

Jitter is derived from a SHA-256 fingerprint of:

```text
retry class
operation_id
idempotency_key
attempt
```

This gives two useful properties:

1. independent operations do not all retry at exactly the same instant;
2. the same operation/attempt computes the same delay after process restart.

Therefore restart does not randomly rewrite an already determined retry schedule.

No private message, prompt, route, or provider response participates in the jitter seed.

## 6. Retry scheduling

`schedule_failed_safe()` accepts only:

```text
state = failed_safe
```

If the attempt budget remains:

```text
failed_safe
    ↓
retry_wait
next_attempt_at = deterministic bounded backoff
```

If the attempt budget is exhausted:

```text
failed_safe
    ↓
exhausted
```

Calling it for `delivery_unknown` fails before any retry state can be written.

## 7. Crash between FAILED_SAFE and RETRY_WAIT

A process may crash after persisting:

```text
failed_safe
```

but before scheduling:

```text
retry_wait
```

HLB-004.3 provides:

```text
schedule_pending_failed_safe()
```

which sweeps durable stranded `FAILED_SAFE` operations after restart.

For batches containing Cognition, reconciliation is mandatory before **any** batch mutation. This prevents a mixed Percept/Cognition sweep from partially advancing Percept while silently skipping the Cognition safety gate.

## 8. Due selection is read-only

`due_operations()` reads retry waits whose:

```text
next_attempt_at <= now
```

It does not mutate state.

Limits are bounded:

```text
1 <= limit <= 1000
```

Timestamps must be timezone-aware ISO-8601. Naive or malformed timestamps fail closed.

## 9. Release is not execution

`release_due()` moves an eligible operation:

```text
retry_wait
    ↓
prepared
```

It does **not** increment `attempt`.
It does **not** call an executor.
It does **not** contact Hermes/Runtime/provider.

Only the later durable attempt boundary increments the count.

Concurrent schedulers are safe: if two schedulers select the same due row, only one durable state transition succeeds; the other observes a state conflict and does not duplicate the claim.

## 10. Cognition reconciliation at three boundaries

Cognition retry safety is checked at three places.

### A. Before scheduling a FAILED_SAFE retry

```text
failed_safe
    ↓ check accepted CognitiveReceipt
    ├─ receipt exists → completed
    └─ none           → retry_wait
```

### B. When a due retry is released

A receipt may arrive while the operation is waiting:

```text
retry_wait
    ↓ check accepted CognitiveReceipt
    ├─ receipt exists → completed
    └─ none           → prepared
```

### C. Immediately before retry attempt start

A receipt may arrive after release but before the retry starts:

```text
prepared (attempt > 0)
    ↓ check accepted CognitiveReceipt
    ├─ receipt exists → completed
    └─ none           → in_flight; attempt += 1
```

This third check closes the release-to-execution race window.

Initial Cognition attempt `attempt=0` does not require receipt reconciliation because no previous attempt exists.

## 11. `begin_attempt()` is still not an executor

`begin_attempt()` performs the durable attempt boundary:

```text
prepared
    ↓ atomic OperationStore transition
in_flight
attempt += 1
```

It returns after the state commit.

It does not invoke Hermes or a provider.

Future service integration must use this durable boundary before external execution so a crash never leaves HLB believing an external operation was never started when it may have been.

## 12. Percept restart recovery

Interrupted Percept:

```text
in_flight
    ↓ process restart
failed_safe
error_code = process_restart_idempotent_replay_safe
    ↓ retry policy
retry_wait / exhausted
```

This is safe because Percept replay is protected by deterministic ingress idempotency.

The retry engine still obeys the five-attempt bound.

## 13. Cognition restart recovery

Interrupted Cognition requires receipt reconciliation.

```text
in_flight
    ↓ restart
check accepted CognitiveReceipt
    ├─ exists → completed
    └─ absent → failed_safe
                   ↓ reconcile again before schedule
               retry_wait / exhausted
```

The second reconciliation is intentional. It closes the race in which a receipt is written immediately after the first negative check.

If the receipt probe itself fails, HLB fails closed and leaves the current durable state unchanged rather than guessing that no receipt exists.

## 14. Contact boundary remains unchanged

HLB-004.3 does not recover interrupted Contact operations into retryable state.

Contact still uses HLB-004.2 conservative crash recovery:

```text
contact + in_flight + owner restart
    ↓
delivery_unknown
```

And the core rule remains:

```text
delivery_unknown
    ✕ schedule_failed_safe
    ✕ retry_wait
    ✕ automatic resend
```

HLB-004.4 is responsible for Contact delivery reconciliation.

## 15. Late Cognition receipt graph amendment

To honor `reconcile_before_retry`, the HLB-004.1 graph now permits:

```text
failed_safe → completed
retry_wait  → completed
prepared    → completed
```

but `OperationStore` permits those late-retry completion transitions only for Cognition with at least one previous attempt.

Contact cannot use these transitions to reinterpret a `FAILED_SAFE` send as delivered.

`delivery_unknown → retry_wait` remains forbidden.

The class-aware transition guard also preserves immutable operation identity (`operation_id`, `kind`, `idempotency_key`, `request_hash`, `created_at`, and schema version). Only `prepared → in_flight` may advance `attempt`, and it must advance by exactly one.

## 16. Hard invariants implemented

1. Retry policy is explicit per action class.
2. All three policies require durable state.
3. Total attempt count is bounded.
4. Backoff is bounded.
5. Jitter is deterministic across restart.
6. Retry scheduling accepts only `FAILED_SAFE`.
7. `DELIVERY_UNKNOWN` never enters retry scheduling.
8. Contact receives at most one retry after a proven safe failure.
9. Retry due selection does not mutate state.
10. Retry release does not execute or increment attempt count.
11. Concurrent schedulers cannot release the same retry twice.
12. Attempt count increments only at `begin_attempt()` / durable start.
13. Stranded `FAILED_SAFE` state is resumable after process crash.
14. Cognition must reconcile accepted receipt before retry schedule.
15. Cognition must reconcile again when retry becomes due.
16. Cognition must reconcile again immediately before retry attempt start.
17. Late Cognition receipt completes the operation instead of recomputing.
18. Receipt-probe failure fails closed.
19. Percept interrupted execution is replay-safe through idempotency.
20. Non-Contact recovery never mutates Contact `in_flight` state.
21. Retry engine never invokes an external executor.
22. Transition guards reject identity mutation and illegal attempt jumps.

## 17. Explicit non-goals

HLB-004.3 does not implement:

```text
provider send reconciliation
Contact delivery_unknown reconciliation
Hermes capability/version discovery
Doctor vNext
route freshness/invalidation
service lifecycle wiring
failure injection suite
24h/72h soak tests
```

It does not own Life Runtime Concern, Memory, Identity, Personality, Motivation, or ContactDecision authority.
